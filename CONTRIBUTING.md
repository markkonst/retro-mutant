# Contributing to Retro Mutant

[Project setup](README.md) · [Documentation guide](docs/README.md)

This is a hobby project: readable explanations and small, reproducible fixes are welcome. You do not need to understand the whole EXE to improve one behavior.

## 1. Get a working baseline

Follow the root README to install dependencies and import your own assets. Then:

```powershell
npm run check
npm run smoke
```

The smoke suite needs local extracted level data; audio checks use original sound JSON where applicable. Record the failing command and output before changing code. A source-only clone can run the TypeScript check/build, but cannot reproduce asset-backed gameplay tests without the user's game files.

## 2. Choose a bounded change

Describe the visible trigger, actual behavior and expected result. Identify the level, source/type or native address if known. A short reproducible case is more useful than claiming “the level is broken”.

Read the corresponding chapter: [VM](docs/scriptvm/README.md), [collisions](docs/collisions/README.md), [audio](docs/audio/README.md), or [levels](docs/levels/README.md). Keep generic logic separate from level-specific rules.

## 3. Evidence and code style

Explain gameplay intent first, then record the DOS address supporting the implementation. Use descriptive TypeScript names and comments for signed comparisons, overflow, fixed-point arithmetic and deliberate timing quirks.

Distinguish a recovered rule from a visual approximation. Do not add another platform's mechanic as though it were confirmed DOS behavior. An unknown branch should remain visible as an uncertainty, not silently become a no-op.

For a new native, record its image/segment, entry offset, inputs, state changes, branch behavior and confidence. Add it to the level handler and update the function catalogue. A candidate address does not become a fully understood function merely because it disassembles.

## 4. Testing

Use the narrow regression for the changed behavior first. Gameplay tests should exercise the trigger and meaningful outcomes: a goal decrement, persistent source change, correct expiry or actual hit/miss.

Run `npm run smoke` for shared runtime changes. The current suite contains 25 programs. Tests that teleport Bart, grant inventory or enable invulnerability isolate mechanics; say so in the documentation. They do not prove an unassisted full playthrough.

For palette changes, check actual decoded colours and restoration. For audio sequencing, use the optional [AdLib oracle](docs/audio/README.md#validation) when needed. Do not require Ghidra or Unicorn merely to build the application.

## 5. Debugging

`npm run dev` starts the server and TypeScript watcher. Reload after compilation. Select an object to inspect PC, waits, branches and blocked-native reasons.

Visual Studio users can open `retro-mutant.slnx` or `retro-mutant.esproj`, choose a browser debug target and press F5. `npm run debug-check` verifies the debug configuration. Source maps are generated by the build. Avoid starting a second server on port 5173.

## 6. Documentation and pull requests

Keep the root README focused on setup and orientation. Explain internals in the relevant chapter and link to the source. Update the collision matrix, level status or function confidence when evidence changes.

A pull request should explain the problem, the resulting behavior, evidence and validation. State remaining limits. Keep documentation in English so it is accessible to the GitHub audience.

Before submitting:

```powershell
git diff --check
node tools/check-repo-assets.mjs
```

Run the asset check after staging, too. Do not force-add original EXE/OVL files, archives, decoded images/JSON/fonts, sound data or oracle traces. They remain local. The project's MIT license covers original contributions, not the original game's material; see the [legal section](README.md#legal-and-attribution).
